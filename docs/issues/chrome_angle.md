# Windows Chrome / ANGLE のフリーズ対策

2026-09-12の拡張・本体への修正と、その後のユーザー確認をまとめる。

## 結論と確認範囲

重いシェーダーの準備中にGPUの完了を同期的に待つ経路と、準備中にも描画・動画転送・リサイズを行う経路があった。同期確認のタイミング、コンパイルの順序、準備中のGPU操作を整理した後、Windows Chromeの拡張についてユーザーから「フリーズがなくなった」「本体より安定している感じ」と確認を得た。

ただし、ANGLEやGPUドライバー内部の停止箇所を特定したわけではない。複数の対策を同時に適用したため、どの1つが決定打だったかも断定できない。「コード上の危険な経路を修正し、ユーザー環境で症状が解消した」という到達点である。

## コード上の問題

### 1. GPU完了前に同期ステータスを取得していた

`COMPILE_STATUS` / `LINK_STATUS`などの確認は、呼び出すタイミングによってはコンパイルやリンクの完了を同期的に待つ可能性がある。重い処理が残っていると、JavaScript側の呼び出しが戻らず、画面や操作が停止したように見える。

本体には、非同期のGPU完了待ちを900msで打ち切った後、まだ未完了でも`LINK_STATUS`を読む経路が残っていた。拡張にも、初期表示用のpassthroughを含め、完了前の同期確認を見直す必要がある箇所があった。

JavaScriptの`setTimeout`では、すでにブロックしている同期WebGL呼び出しを中断できない。タイムアウトを設けるだけでは、この問題への対策にならない。

### 2. 準備中にも別のGPU操作を重ねていた

シェーダー準備中にも動画テクスチャの転送、描画、Canvasの描画バッファのリサイズが進み得た。重いコンパイルとこれらの操作が重なることは、GPU負荷や同期待ちを増やす要因になる。

これが実機でどの程度フリーズに寄与したかは単独では測定していない。

### 3. 複数パスの投入と無期限待ちがあった

拡張のOverlayには、複数パスを投入してからまとめて待つ処理があった。また、コンパイル枠の取得やGPU完了待ちに無期限ループが残っていた。

コンパイル枠のTTLは3秒で、延長が描画側のタイマーに依存していた。長い同期ブロックで延長できなくなる状況も考慮が必要だった。

## 9/12に行った対策

| 対策 | 内容 |
| --- | --- |
| 完了確認の順序 | `KHR_parallel_shader_compile`が使える場合、`COMPLETION_STATUS_KHR`で完了を確認してからリンク結果を検証する。未完了のまま同期ステータス確認へ進まない。 |
| 順次コンパイル | 拡張ではパスごとに「投入 → 完了待ち → 検証」を終えて次へ進む。複数描画面・タブ間の順番制御も維持する。 |
| 描画パスの分割 | 既存のBeam分割を生かし、sampling・composite・phosphorの処理分割を拡張へ反映する。 |
| 準備中のGPU操作の抑制 | 動画転送・描画・描画バッファのリサイズを止める。本体ではピクセル読み戻しも抑え、リサイズは最新の要求を保持して準備完了後に反映する。 |
| 待機上限 | GPU完了待ちは15秒。拡張のコンパイル枠取得は30秒、メッセージ応答は2秒を上限にする。 |
| 枠の保持 | 拡張のコンパイル枠TTLを30秒に延ばし、heartbeatに加え各パス直前・有効化直前に保持権を確認する。 |
| 失敗後の停止 | タイムアウトした本体パイプラインには追加描画・コンパイルを行わない。同じ失敗を毎フレーム再試行しない。 |
| 再利用 | 拡張では同じCanvas/WebGLコンテキストを維持し、パス単位・バリエーション単位のキャッシュを使う。uniform変更だけで済む設定では再コンパイルしない。 |
| 中断と解放 | 停止・破棄・設定変更・コンテキスト喪失を確認し、古い処理結果を適用しない。GPU完了未確認の状態で同期的な強制解放を重ねない。 |

拡張のOverlayは準備中に元動画を表示する。本体では準備中の映像更新を一時停止し、完了後に最新の設定・サイズで再開する。

## なぜ改善したと考えられるか

問題は「シェーダーのコンパイルが遅い」だけではなく、その間に同期確認や別のGPU操作を行う構造にあったと考えられる。

修正により、重い処理の完了を非同期で確認しながら待ち、準備中のGPU操作を抑え、完了できない場合は追加処理を止める形になった。Windowsでのフリーズ解消は、この組み合わせによるものと考えられるが、ANGLE内部のデッドロック等を実証したものではない。

## 検証と残る制約

- 拡張の修正時には17件のモックテストが通過。パス順序、完了前の同期確認回避、キャッシュ、タイムアウト、中断などを検証した。
- 本体への安定化反映時には全30件が通過。追加テストでは900msを超える待機、15秒タイムアウト、準備中の描画停止・リサイズ保留などを確認した。
- 上記の件数は当時の記録であり、現在のテスト総数ではない。
- モックテストは実際のGLSLコンパイルやGPUドライバーの動作を再現しない。実機での改善確認はユーザー報告による。
- `KHR_parallel_shader_compile`がない環境では、短く待った後に同期確認する経路が残る。
- JavaScript側から同期WebGL呼び出し自体を中断する仕組みではなく、すべてのGPU・ドライバーで停止を防ぐ保証はない。
- 古いWindows機で後に報告された断続的な停止・音切れは別の性能課題として扱った。フリーズ対策がすべての負荷問題を解消したわけではない。

## 後日のPreview Dialogの問題との区別

9/13の漫画プレビューで発生した初期サイズの揺れは、CanvasのレイアウトとAuto Targetの反映順を修正して解消したとユーザー確認を得た。その修正ではLinkingの待機処理は変更していない。

また、漫画のページ送りでRetroPlayerを再生成しない変更は、その後の独立した最適化である。これらを9/12のWindows ANGLEフリーズの原因・対策と混同しない。

## 2026-09-13: Capture Tab（viewer.js）への反映

後日の確認で、Capture Tabにはコンパイル直後の`COMPILE_STATUS`取得と、passthroughのリンク直後の`LINK_STATUS`取得が残っていた。9/12のOverlay修正とは別に、以下を反映した。

- Overlayの`createProgramCache`を共有し、passthrough・通常パス・Beam補助パスを順次コンパイルする。
- KHRが利用可能なら完了を確認してから`LINK_STATUS`を読む。GPU待ちの上限は15秒。
- 同一コンテキストのプログラムを再利用し、設定変更で重複コンパイルしない。
- 設定が連続変更された場合、進行中のパスの完了を待って最新要求へ移る。古い要求を有効化しない。
- 準備中は動画転送・描画・uniform更新・Canvasバッファのリサイズを停止し、成功後に現在のサイズと設定を反映する。
- 失敗・タイムアウト時は追加のGPU操作を止め、viewer再読み込みを案内する。ページ終了時は待機を中断する。
- KHRがない環境の同期確認フォールバックは残る。`synchronous-link-fallback`で明示する。

初期表示用passthroughも含めて準備が完了するまでは描画を開始しない。切り替え中は直前の描画を保持する。
この追加修正のWindows実機検証は未実施。モックで完了前の同期確認禁止、順序、キャッシュ、タイムアウト後の停止、描画・リサイズ抑止を検証する。
