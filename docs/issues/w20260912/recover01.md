# Windows Chrome extension 復旧計画（2026-09-12）

## 目的

Windows Chrome の YouTube などで、extension のフィルターを安定して使えるようにする。
本体では ANGLE 周辺の問題がだいぶ改善しているため、本体の描画パイプラインを基準に、extension に反映されていない改善を移す。

中心となる対象は `extension/overlayRuntime.js`。`extension/viewer.js` の Capture Tab 経路も比較・回帰確認する。
Windows 実機での停止箇所はまだ特定していない。以下のコード上の問題と、実際のフリーズ原因は区別して扱う。

- ローカル `main` の先端と比較すると、extension 内は8ファイル変更されている。
- 過去の対応で、コンパイルの順番制御、Beam の描画パス分割、Windows 向けの動画プロキシなどが追加されている。
- 既存の問題メモでは、Overlay はフリーズやフィルター未適用があり、Capture Tab は比較的安定していると記録されている。現在の実機でも同じかは再確認する。
- JS 29ファイルの構文、静的 import の参照先、manifest の公開リソースの存在確認は通過。実際のシェーダーコンパイル・Windows 動作を保証する確認ではない。

## 本体との主な差分

| 項目 | 本体 | Overlay |
| --- | --- | --- |
| コンパイル順序 | パス単位で完了を待ち、次へ進む | 複数パスを投入してから、まとめて完了を待つ |
| 再利用 | パス・設定バリエーション単位のキャッシュあり | バリエーション変更時に描画面を破棄して作り直す |
| 中断・待機 | 破棄、コンテキスト喪失、設定変更の確認とポーリング上限あり | コンパイル枠と GPU 完了待ちに無期限ループが残る |
| 描画パス | sampling・composite・phosphor なども分割 | Beam の分割は一部反映済みだが、構成全体は揃っていない |

本体も完全に非同期とは限らない。現在の実装は GPU 完了待ちを900msで打ち切った後、`LINK_STATUS` を取得するため、この値をそのまま移すだけでフリーズが解決するとは考えない。

## 作業順序

### 1. 停止箇所を確認できるようにする

既存の状態表示を利用し、必要な箇所に診断ログを追加する。

- シェーダーのパス名、コンパイル・リンク・完了待ち・有効化の開始と終了、所要時間。
- 初回の動画転送と、初回のフィルター描画の開始と終了。
- コンテキスト喪失、設定変更による中断、コンパイル枠の取得・解放。
- プリセットと実際に選択された描画パス。

通常の毎フレーム出力は避ける。停止が起きたときに、最後に開始した処理と最後に完了した処理を追えるようにする。
Windows では変更前の状態も記録し、修正ごとの比較基準を残す。

### 2. コンパイルの実行単位を本体に揃える

- パスごとに「投入 → 完了待ち → リンク検証」を終えてから次へ進める。
- 初期表示用の passthrough も対象にする。現在残っている直後の `COMPILE_STATUS` / `LINK_STATUS` 取得を見直す。
- 複数描画面・タブ間の順番制御と、各パスの順次コンパイルを組み合わせる。
- `background.js` の枠は TTL が3秒で、延長は描画側のタイマーに依存する。長いブロックで期限切れになった場合や、保持権を失った場合の扱いを定義する。

単に `setTimeout` を挟むことを非同期化の完了条件にしない。

### 3. 待機・失敗・中断から確実に復帰させる

- コンパイル枠取得と GPU 完了待ちに、上限および中断条件を設ける。
- Overlay 停止、描画面破棄、コンテキスト喪失、設定変更後に、不要な処理を進めない。
- メッセージ送信失敗時に無期限で枠取得を繰り返さない。
- 成功・失敗・中断のいずれでも、枠、heartbeat、状態表示、作成途中のリソースを適切に片付ける。
- 非同期コンパイルの失敗を描画面に伝え、「コンパイル中」のまま残さない。

JavaScript 側のタイムアウトでは、既にブロックしている同期 WebGL 呼び出しは中断できない。待機ループの終了対策と、同期ブロックの回避は別々に確認する。

### 4. コンパイル済みプログラムを再利用する

- 本体のパス単位キャッシュと、同じコンパイルの重複を防ぐ仕組みを参考にする。
- 設定変更時も可能な限り同じ WebGL コンテキストを維持し、必要なプログラムを差し替える。
- uniform の変更だけで済む設定では再コンパイルしない。
- 作成済みのプリセットへ戻したときに再コンパイルされないことを確認する。

WebGLProgram は別コンテキストへ流用できないため、キャッシュはコンテキスト単位で管理する。

### 5. 本体の描画パスとの未反映差分を埋める

- sampling・composite・phosphor の分割を比較し、必要なシェーダーと描画順序を移す。
- Beam は追加済みの分割を生かし、uniform・中間テクスチャ・設定の対応を本体と照合する。
- Overlay の sampling モードの数値対応、および stripe モードが `modern` ではなく `next` を判定している不一致を修正する。
- 同期スクリプトに新しいシェーダーが漏れていないか確認し、必要な生成処理と manifest の公開設定を揃える。

コンパイル制御の修正と描画パスの移植は段階を分け、どの変更で挙動が変わったか追えるようにする。

### 6. Overlay 独自の失敗処理を修正する

- 動画の `texImage2D` が一度50msを超えただけで、その動画を除外する処理を見直す。単発の遅延と、描画不能なエラーを分ける。
- WebGL を取得済みの canvas に `getContext("2d")` を呼んでも切り替えられないため、2D 退避が必要なら別 canvas を用意する。
- フォールバック中の例外によって次の `requestAnimationFrame` が予約されず、描画ループ全体が停止する経路を修正する。
- Windows の `captureStream()` / プロキシ動画 / `ImageCapture` 経路について、準備未完了・失敗・停止時の挙動を確認する。

2D 退避だけをもって完了とはしない。目的はフィルターを適用した状態での安定動作。

## 実施結果（2026-09-12 / recover01）

### 実装した内容

- `extension/shared/overlayCompiler.js` に、コンテキスト単位のプログラムキャッシュと順次コンパイルを追加した。
- passthrough を含む各パスで、GPU 完了待ちの後にリンクを検証する。設定切り替えでは同じ canvas / WebGL コンテキストを維持し、同じソースは再利用する。
- GPU 完了待ちは15秒、コンパイル枠の待機は30秒、メッセージ応答は2秒を上限とした。停止・設定変更・コンテキスト喪失時に中断する。
- コンパイル枠の TTL を30秒に変更し、heartbeat に加えて各パスの直前と有効化の直前に保持権を確認する。
- コンパイル中は元動画を表示し、Overlay の動画転送・描画と canvas のバッファリサイズを止める。
- sampling の前処理、composite の適用、phosphor の本体処理と後処理を分割した。中間描画では処理済みのテクスチャを次のパスへ渡す。
- sampling と composite の設定が `normalizeSettings` で失われていた問題を修正した。プリセット同期にも対応するフィールドを追加した。
- sampling の数値対応と `modern` stripe の判定を修正した。入力の反転を最初のパスで行い、後段で二重に反転しないよう整理した。
- 50msを超えた単発の動画転送を、動画除外ではなく診断記録に変更した。
- 2D への退避では canvas を交換する。描画面ごとに例外を処理し、1面の失敗で描画ループ全体を止めない。
- 動画の readyState 変化だけでプロキシを作り直さないようにした。以前の対象から遅れて届いた bitmap は破棄し、プロキシの準備が進まない場合は元動画を使う。
- `Save overlay diagnostics` ボタンをポップアップへ追加した。コンパイル、初回転送、初回の各描画パス、エラーなど直近200件のイベントと設定を JSON 保存できる。
- 新規シェーダーの同期漏れと公開リソースを補い、`scripts/check-extension.mjs` で構文・import・Overlay が使うモジュールの公開設定を確認するようにした。

本体のファイルと Capture Tab の `viewer.js` は変更していない。ただし共有設定・プリセットの変更は Capture Tab にも反映されるため、実機での回帰確認は必要。

### Windows で試す手順

1. `release/tetorica-retro-tab-filter-extension-v0.42.32.zip` を展開する。リポジトリを使う場合は `extension` ディレクトリをそのまま使ってもよい。
2. Chrome の `chrome://extensions` で開発者モードを有効にし、展開したフォルダーを「パッケージ化されていない拡張機能を読み込む」で登録する。既存の読み込み先を更新した場合は、その拡張を再読み込みする。
3. YouTube のタブも再読み込みする。既に注入された古いモジュールは、拡張だけを再読み込みしても残る場合がある。
4. 描画対象1面で Overlay を起動し、まず標準の Phosphor Dot、次に CRT Beam で確認する。元動画表示からフィルター表示に切り替わるか、切り替え中に操作できるかを見る。
5. プリセットを変更して戻す、シーク、一時停止・再生、Overlay 停止・再開を試す。上下左右の向きとフィルターの見た目も本体と比較する。
6. 問題があれば、対象タブを開いた状態でポップアップの `Save overlay diagnostics` を押す。Windows / Chrome のバージョンと GPU、`chrome://gpu` の ANGLE backend も記録する。
7. Capture Tab と Mac Chrome の回帰、複数面・複数タブは上記が通ってから確認する。

診断ログの `draw-submitted` は JavaScript の描画呼び出しが戻ったことを示し、GPU 上での描画完了を意味しない。完全にフリーズしている間は診断保存も応答しない可能性がある。その場合は事前に DevTools Console の Verbose と Preserve log を有効にし、`[tetorica-overlay]` の最後のイベントを確認する。JSON のイベントはメモリ上の記録で、タブの再読み込み後には引き継がれない。

### 未検証・制約

- このセッションには操作可能な Chrome 接続がなく、Mac Chrome の画面確認と Windows 実機検証は未実施。
- `KHR_parallel_shader_compile` が利用できない環境では、短い待機後の `LINK_STATUS` が同期的にブロックする可能性が残る。ログには `synchronous-link-fallback` と記録する。
- GPU 完了を確認できないまま中断したリソースには同期的な `loseContext()` を使わない。完了確認が可能なら遅延解放し、確認できないものはコンテキストの回収に任せる。
- 本体の全描画機能・バッファサイズ制御を完全に共通化した変更ではない。見た目と処理負荷の一致は実機で確認する。
- したがって、この時点の到達点は「修正版の実装・ローカル検証・ZIP 作成」。Windows の問題を解決済みとは扱わない。
