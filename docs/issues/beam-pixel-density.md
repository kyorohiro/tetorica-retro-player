# macOS Chrome / Safari の Beam spacing 比較

## 観測と未確定事項

Chrome の spacing 3.8、Safari の 2.8 付近で良い表示になるという報告がある。
Target width は約221が目安。両ブラウザーの実測サイズはまだ比較していない。
spacing の差だけでは CSS 幅、描画密度、シェーダーのどれが原因か確定しない。

現状の auto target は、Render cap 後の表示領域を CSS px で測り、
横長・正方形は spacing X、縦長は Y で割って元画像のアスペクト比を維持する。
Canvas の解像度は別に `max(renderResolutionScale, clamp(DPR, 1, 2))`
を使って計算し、その後に Render cap などの制限を適用する。
従って DPR と実際の Canvas / CSS 比は必ずしも一致しない。
既存の CSS px 単位の spacing に DPR を追加で掛ける変更は、まだ行っていない。

## 比較手順（DevTools不要）

1. 同じMac・ディスプレイ・画像・preset・表示モード・Render cap設定で比較する。
2. 最初は spacing も同じ値にし、レイアウトとシェーダーの準備完了を待つ。
3. プレビュー左上の **px** ボタンを押す。
4. Chrome / Safari の CSS、Canvas、描画 px / CSS px、DPR、設定Targetを比較する。

情報は絶対配置で画像に重ねるため、表示の開閉で描画領域のサイズを変更しない。
開いている間だけ1秒ごとにDOMのサイズを読み取る。GPUへの問い合わせはしない。
テキスト欄は選択・コピー可能。閉じると定期読み取りも停止する。

- CSSサイズが違うなら表示領域・ズーム・レイアウトを確認する。
- CSSサイズが同じで描画 px / CSS px が違うなら、解像度設定・DPR・cap を確認する。
- サイズ適用が待機中の場合は、完了してから比較する。
- サイズと密度が揃っても差があるなら、サンプリングやシェーダー側の差を調べる。

設定Targetは設定上の値で、Beam / Phosphorの中間パスの実サイズではない。
密度差が原因と確認できてから補正方法を決める。現時点でモアレ修正済みとは扱わない。

## 2026-09-13: 小数DPRへの追従

ユーザー確認ではChromeも元の表示倍率に戻すとspacing 1.0でモアレが消えた。
ブラウザー固有のspacing補正より、表示倍率による再サンプリングを先に扱う。

自動解像度のDPR整数丸めを廃止。DPR 1.5では、手動解像度設定が1なら
Render scaleも1.5になる。解像度変更では既存Canvasのサイズを更新し、
WebGLコンテキストを作り直さない。CSSサイズが一定でもresolutionメディアクエリで
DPR変更を検知し、window resizeも補助的に監視する。
コンパイル後の遅延レイアウト更新も最新の解像度を読む。

自動解像度の下限1・上限2、手動の高解像度設定、Render capは維持する。
その制約やピンチズーム、CSS変形がある場合、物理ピクセルとの完全一致は保証しない。
spacingの自動補正やシェーダーのアンチエイリアスは今回変更しない。

確認は手動解像度1で、Chromeを問題の倍率に戻し、px表示のDPRとRender scaleが
ともに1.5になること、spacing 1.0での模様を比較する。実機での効果は未確認。

## 縮小時に残るモアレへの追加対策

小数DPR対応後も縮小でモアレが出るとの報告を受けて追加した。
以下が最新仕様で、前節の「下限1」は廃止した。

- 手動解像度1ではDPR 1未満も使う。Canvasサイズ計算の下限1倍も廃止。
  手動解像度が1より大きければ従来どおりその解像度を最低値とする。
- CSSサイズのデバイスピクセルへの丸めもDPR 1未満に対応。
- crisp / smooth判定にはCSSサイズ×DPRを使い、CSS上だけ大きい画像を
  拡大と判定しないようにする。
- Beamの内部target制限に表示ピクセルと描画バッファの小さい方を反映。
  既存の最小セル1.2 CSS pxがDPR 2で確保していた2.4描画px相当を基準に、
  DPRが低いときは内部targetを減らす。既存のcapやbloomの制限も維持。
  縦横比は既存のtarget制限処理で維持する。Phosphorの制限は変更しない。

この2.4pxは従来のDPR 2表示を保つための基準で、全画像でモアレをなくす
保証値ではない。縮小時に細部が粗くなるトレードオフがある。
設定Targetとspacing自体は書き換えないため、px表示の「設定Target」は
この内部補正後のtargetとは異なる。シェーダーソースも変更しない。

100%・80%・33%の同じ画像で確認する。33%ではDPRとRender scaleが約0.67となる。
型チェックおよび本体72テストは通過。モアレの見た目は実機確認待ち。

## Safariのページズーム（⌘＋／⌘−）

実測ではDPRは2のまま、外幅1085に対しVisual viewport幅が
1085 → 1276.47 → 1446.67へ変化した。高さも同じ倍率で変わった。
DPRだけを使う補正ではこの縮小を検知できなかった。

Safari向けに起動時からの相対ページ倍率を追跡する。
外寸・DPRが変わらず、Viewportの縦横が同じ比率で変わり、
Visual viewport scaleが1のときに限り、その比率を積算する。
ウィンドウ外寸変更や片軸だけの変更は基準測定だけ更新し、倍率には加えない。
推定値はプレイヤー間で共有し、ページ送りでリセットしない。
ChromeではDPRにズームが含まれるため、この推定を適用しない。

補正後の密度はCanvas解像度、Beamの内部target制限、表示サイズの丸め、
拡大縮小の判定に使用する。px表示には補正後密度と起動時基準の推定倍率を追加。

検証時は **⌘0 → ページ再読み込み → pxを開く → ⌘−** の順で操作する。
報告の85%・75%相当では、補正後密度が約1.7・1.5になる想定。
絶対ズームを取得するAPIではないため、縮小したまま起動した場合はその状態が基準になる。
外寸変更とズームの同時操作などは判別できず、この推定は全ケースを保証しない。
モアレの改善はSafari実機での確認待ち。
